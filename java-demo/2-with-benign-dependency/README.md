# Variant 2 — `with-benign-dependency`

Same Spring Boot Hello-World app as variant 1, plus a *benign* version
of `spring-build-analyzer` at version **0.0.0**.

The benign analyzer is a pared-down copy of
[Jeremy Long's `analyzer/spring-build-analyzer`](https://github.com/jeremylong/malicious-dependencies/tree/main/analyzer/spring-build-analyzer)
with two changes:

- The version is set to `0.0.0` (so it doesn't collide with Jeremy's
  `0.0.1-SNAPSHOT` in the local Maven repo).
- The sibling `build-helper` module — the thing that *injects the
  malicious payload classes into the JAR at build time* — is **not
  built**. The standalone `spring-build-analyzer` source tree contains
  exactly one `.java` file, `AnnotationValidationProcessor.java`, and
  it does nothing but iterate over `@SpringBootApplication`-annotated
  classes during compilation.

The result is an annotation processor that's wired up correctly (it
ships a valid `META-INF/services/javax.annotation.processing.Processor`
registration) but does no actual harm — exactly the shape a *real*
build-tooling Maven plugin would have.

```
│       └── resources/META-INF/services/javax.annotation.processing.Processor
└── sboms/

```

## Reproduce

```sh
# from the repo root:
java-demo/scripts/build-and-sbom.sh 2-with-benign-dependency
```

That is equivalent to:

```sh
# 1. build & install the benign analyzer (it lands in the shared local Maven repo
#    at java-demo/.m2-cache/, where the demo's build can resolve it)
docker run --rm \
    -v "$PWD/analyzer:/work" -w /work \
    -v "$(pwd)/../.m2-cache:/root/.m2" \
    maven:3.9-eclipse-temurin-17 \
    mvn -B clean install

# 2. build the demo's fat JAR
docker run --rm \
    -v "$PWD:/work" -w /work \
    -v "$(pwd)/../.m2-cache:/root/.m2" \
    maven:3.9-eclipse-temurin-17 \
    mvn -B package -DskipTests=true

# 3. SBOM the fat JAR with cdxgen -c
docker run --rm \
    -v "$PWD:/app" -w /app \
    -v "$(pwd)/../.m2-cache:/home/cdx" -e HOME=/home/cdx \
    -u "$(id -u):$(id -g)" \
    --tmpfs /tmp:exec,uid=$(id -u),gid=$(id -g) \
    ghcr.io/cyclonedx/cdxgen:latest \
    -t jar -c -o /app/sboms/sbom-cdxgen-c.json /app/target/demo-0.0.1-SNAPSHOT.jar
```

## What the SBOM contains

32 components — the 30 from variant 1, plus:

- `pkg:maven/io.github.jeremylong.spring.analyzer/spring-build-analyzer@0.0.0`
- `pkg:maven/com.squareup/javapoet@1.13.0` (transitive)

The `spring-build-analyzer` component carries a `Namespaces` property
listing **2** classes:

```
io.github.jeremylong.spring.analyzer.spring_build_analyzer.HelpMojo
io.github.jeremylong.spring.build.analyzer.AnnotationValidationProcessor
```

`HelpMojo` is auto-generated by `maven-plugin-plugin`.
`AnnotationValidationProcessor` is the only handwritten class. That
one-to-one match between source files and emitted classes is the
"healthy" baseline. Variant 3 will break it.

## Note on the `-proc:none` flag

The benign analyzer's `pom.xml` configures `maven-compiler-plugin`
with `<proc>none</proc>`. This is a build-system quirk, not a
security choice: the analyzer ships a Processor registration whose
target class (`AnnotationValidationProcessor`) is being compiled in
the same `javac` invocation. Without `-proc:none`, `javac` tries to
load the processor before its `.class` file exists and fails with
*"Provider … not found."*

Jeremy Long's PoC sidesteps this by placing the registration in
`src/main/resources/javax.annotation.processing.Processor` (the JAR
root, not under `META-INF/services/`). The `build-helper` test phase
is what populates the *real* `META-INF/services/` registration that
consumer `javac`s pick up. We don't reproduce that machinery here
because we want the benign analyzer's published source tree to
*completely* match its built JAR — that's the property the variant 2
→ 3 namespace diff exploits.
